# Análisis de riesgos

Escala de probabilidad e impacto: Baja, Media, Alta.
Responsable de todos los riesgos: el propio alumno (trabajo individual).

| Código | Riesgo | Probabilidad | Impacto | Prevención | Respuesta | Responsable |
|---|---|---|---|---|---|---|
| RS01 | **Tiempo.** Las 38 horas de desarrollo ocupan casi todo el tiempo disponible hasta mediados de febrero. Las tareas pueden costar más de lo estimado y los exámenes y las demás asignaturas del grado semipresencial reducen las horas semanales. | Alta | Alta | Empezar justo después de los exámenes, reservar un bloque fijo cada semana (la hora de clase y unas 3 horas en casa), seguir el orden de los hitos y comparar cada semana las horas reales con las estimadas. | Reasignar las tareas pendientes a las semanas siguientes y usar febrero como margen. Si aun así no llega, recortar a lo estrictamente obligatorio (R01 a R06), dejar fuera las funciones deseables y avisar al profesorado. | Alumno |
| RS02 | **Tecnología nueva.** Es la primera vez que se usan Laravel, React con TypeScript e Inertia.js, y pueden aparecer bloqueos que consuman horas. | Alta | Media | Partir de la plantilla oficial de Laravel con React e Inertia.js, empezar por las tareas más sencillas (BASE-1, R01) y seguir la documentación oficial y los materiales del profesorado. | Consultar al profesorado cuando una tarea lleve más del doble de su estimación y simplificar esa tarea hasta que cumpla su criterio de aceptación. | Alumno |
| RS03 | **Despliegue.** Los contenedores pueden no arrancar o comportarse distinto en otro equipo. En Attendize ya fue necesario modificar el Dockerfile para que funcionara. | Media | Alta | Documentar los pasos de arranque en el README, fijar las versiones de las imágenes y probar el arranque desde cero al terminar cada hito. | Volver a la última etiqueta de Git que funcionaba y reconstruir los contenedores desde ahí. | Alumno |
| RS04 | **Pérdida de datos o de código.** Un borrado accidental, un fallo del equipo o un error de Git pueden hacer perder trabajo o los datos de prueba. | Baja | Alta | Hacer commits frecuentes con push a GitHub, crear una etiqueta al cerrar cada hito, tener datos de prueba reproducibles con un script y hacer una copia de la base de datos antes de cualquier migración. | Recuperar el código desde GitHub y volver a crear los datos de prueba con el script. | Alumno |
| RS05 | **Seguridad.** Una validación hecha solo en el navegador, o contraseñas y claves subidas al repositorio, dejarían expuestos los datos de las reservas (nombres y correos). | Media | Alta | Validar siempre en el servidor (R04 y R05), usar el cifrado de contraseñas que trae Laravel, mantener el archivo de configuración con claves fuera de Git y trabajar solo con datos ficticios. | Revisar con una lista de comprobación antes de cada entrega y cambiar cualquier clave que haya llegado al repositorio. | Alumno |
| RS06 | **Dependencias.** Una actualización de paquetes de PHP o de JavaScript puede romper la aplicación o hacer incompatibles dos librerías. | Media | Media | Instalar versiones estables, conservar los archivos de bloqueo de versiones (composer y npm) en el repositorio y no actualizar paquetes durante el desarrollo. | Volver al último commit que funcionaba y recuperar los archivos de bloqueo de versiones. | Alumno |
| RS07 | **Tecnología antigua de Attendize.** Los datos de Attendize pueden no coincidir con lo supuesto en la tabla de correspondencia del punto 8, y la migración quedaría incompleta. | Media | Media | Comprobar las tablas reales de Attendize antes de implementar y probar siempre la migración sobre una copia, nunca sobre los datos originales. | Reducir la migración a lo mínimo (eventos y reservas) o usar datos de prueba ficticios, anotando la decisión en el informe de migración. | Alumno |
